# HSE Tech — پلتفرم آموزشی ایمنی، بهداشت و محیط زیست

پلتفرم آموزشی B2C برای برگزاری دوره‌های تخصصی HSE: فروش دوره، برگزاری کلاس آنلاین
و آفلاین، آزمون، صدور گواهی و استعلام عمومی گواهی.

| موضوع | فناوری |
|---|---|
| زبان | Python 3.12 |
| فریم‌ورک | Django 5.2 LTS |
| قالب | Django Templates + Bootstrap 5 (محلی) |
| دیتابیس توسعه | SQLite |
| دیتابیس Production | PostgreSQL |
| سرور Production | Ubuntu + Gunicorn + Nginx |

> **وضعیت فعلی: فاز ۵ — احراز هویت (تطبیق کد ملی و شماره موبایل).**
> نقشه راه کامل: [`docs/roadmap.md`](docs/roadmap.md) · معماری و دیتابیس: [`docs/architecture.md`](docs/architecture.md)

## راه‌اندازی پروژه روی سیستم شما

پیش‌نیاز: **Python 3.12** و **Git** نصب باشند. برای بررسی:

```bash
python --version
git --version
```

### ۱. دریافت پروژه

```bash
git clone <آدرس-مخزن>
cd HSE-academy
```

### ۲. ساخت محیط مجازی (Virtual Environment)

محیط مجازی یک پوشه جداست که کتابخانه‌های این پروژه فقط داخل آن نصب می‌شوند و با
سایر پروژه‌های سیستم شما تداخل پیدا نمی‌کنند.

**ویندوز:**

```bat
python -m venv .venv
.venv\Scripts\activate
```

**لینوکس / مک:**

```bash
python3 -m venv .venv
source .venv/bin/activate
```

بعد از فعال شدن، ابتدای خط ترمینال عبارت `(.venv)` را می‌بینید. **تا وقتی این را
نمی‌بینید، دستورهای بعدی را اجرا نکنید.**

### ۳. نصب کتابخانه‌ها

```bash
pip install --upgrade pip
pip install -r requirements.txt
```

### ۴. ساخت فایل تنظیمات `.env`

**ویندوز:**

```bat
copy .env.example .env
```

**لینوکس / مک:**

```bash
cp .env.example .env
```

فایل `.env` رمزها و کلیدهای شماست و **هرگز داخل گیت ذخیره نمی‌شود**. برای شروعِ
توسعه، مقادیر پیش‌فرض کافی است و نیازی به تغییر ندارند.

### ۵. ساخت جدول‌های دیتابیس

```bash
python manage.py migrate
```

### ۶. ساخت کاربر مدیر

نام کاربری سایت **شماره موبایل** است، نه username.

```bash
python manage.py createsuperuser
```

### ۷. اجرای سرور

```bash
python manage.py runserver
```

حالا در مرورگر باز کنید:

- سایت: <http://127.0.0.1:8000/>
- پنل مدیریت: <http://127.0.0.1:8000/admin/>
- بررسی سلامت: <http://127.0.0.1:8000/health/>

برای خاموش کردن سرور، در ترمینال `Ctrl + C` بزنید.

> **هر بار که پنجره ترمینال را می‌بندید و دوباره باز می‌کنید**، قبل از هر کاری
> این دو دستور را اجرا کنید — وگرنه پایتون پروژه را پیدا نمی‌کند:
>
> ```bash
> cd مسیر/پروژه/HSE-academy
> .venv\Scripts\activate        # ویندوز
> source .venv/bin/activate      # لینوکس و مک
> ```

## دستورهای کمکی محیط توسعه

### ساخت داده نمونه

تا صفحه اصلی پر و واقعی به نظر برسد و بتوانید طراحی را ببینید:

```bash
python manage.py seed_demo
```

برای پاک کردن داده نمونه قبلی و ساخت مجدد:

```bash
python manage.py seed_demo --reset
```

### ساخت گروه‌های نقش

نقش‌های سایت (مدیر، مدرس، مدیر محتوا، پشتیبانی، مالی، دانشجو) و دسترسی هر کدام:

```bash
python manage.py setup_groups
```

اجرای چندباره‌اش بی‌خطر است. برای دادن نقش به کاربر: پنل مدیریت ← کاربران ←
انتخاب کاربر ← بخش «دسترسی‌ها» ← افزودن گروه.

### ساخت یا بازنشانی حساب مدیر

دستور استاندارد `createsuperuser` رمز را نامرئی می‌گیرد و اگر اشتباه تایپ شود
راهی برای فهمیدنش نیست. این دستور رمز را روی صفحه نشان می‌دهد:

```bash
python manage.py make_admin 09121234567 hse12345
```

دیدن حساب‌های موجود:

```bash
python manage.py make_admin --list
```

> این دستور فقط در محیط توسعه کار می‌کند. روی سرور از `createsuperuser` و
> `changepassword` استفاده کنید.

## پنل پیامک

در محیط توسعه نیازی به پنل پیامک نیست. `USE_MOCK_SMS=True` است و کد تأیید
به‌جای ارسال، **در ترمینال چاپ می‌شود**:

```
============================================================
  پیامک آزمایشی (ارسال واقعی انجام نشد)
  گیرنده : 09121234567
  متن    : 483927
============================================================
```

### وقتی پنل واقعی خریدید

در فایل `.env`:

```env
USE_MOCK_SMS=False
SMS_PROVIDER=kavenegar
SMS_API_KEY=کلید-پنل-شما
SMS_SENDER_NUMBER=شماره-خط-شما
SMS_OTP_TEMPLATE=نام-الگو        # اختیاری، ارسال با الگو ارزان‌تر است
```

هیچ کد دیگری تغییر نمی‌کند. اگر پنل دیگری خریدید، از روی کلاس
`KavenegarSmsProvider` در `apps/accounts/services/sms.py` یکی مشابه بسازید
و نامش را به دیکشنری `PROVIDERS` اضافه کنید.

> در محیط توسعه حتی اگر کلید پنل واقعی در `.env` باشد، باز هم نسخه آزمایشی
> استفاده می‌شود — تا به اشتباه از اعتبار پنل خرج نشود.

### تنظیمات کد یکبارمصرف

| متغیر | پیش‌فرض | معنی |
|---|---|---|
| `OTP_EXPIRY_SECONDS` | ۱۲۰ | اعتبار کد (ثانیه) |
| `OTP_MAX_ATTEMPTS` | ۵ | حداکثر تلاش برای هر کد |
| `OTP_RESEND_COOLDOWN_SECONDS` | ۹۰ | فاصله لازم بین دو ارسال |
| `OTP_MAX_SENDS_PER_HOUR` | ۵ | سقف درخواست کد در ساعت |

## سرویس احراز هویت (تطبیق کد ملی و موبایل)

در محیط توسعه نیازی به خرید سرویس نیست. رفتار شبیه‌سازی با
`MOCK_IDENTITY_RESULT` در `.env` کنترل می‌شود:

| مقدار | نتیجه |
|---|---|
| `matched` | همیشه تطبیق دارد (پیش‌فرض) |
| `not_matched` | همیشه تطبیق ندارد — برای تست پیام خطا |
| `failed` | همیشه خطای سرویس — برای تست قطعی سرویس |
| `by_national_code` | ختم به ۰۰ تطبیق ندارد، ختم به ۹۹ خطا |

> کد ملی باید رقم کنترلی درست داشته باشد وگرنه فرم قبل از تماس با سرویس
> ردش می‌کند. نمونه کد معتبر برای تست: `0499370899`

### وقتی سرویس واقعی را خریدید

```env
USE_MOCK_IDENTITY=False
IDENTITY_PROVIDER=shahkar
IDENTITY_API_BASE_URL=آدرس-سرویس
IDENTITY_API_KEY=کلید-شما
```

نام فیلدهای درخواست و پاسخ را در `apps/accounts/services/identity.py`
مطابق مستندات سرویسی که خریدید تنظیم کنید. بقیه پروژه دست‌نخورده می‌ماند.

### اجباری بودن احراز هویت

```env
IDENTITY_REQUIRED_FOR_REGISTRATION=True   # پیش‌فرض
```

با `True` بدون تطبیق هویت حساب ساخته نمی‌شود. با `False` کاربر ثبت‌نام
می‌کند اما تا تکمیل احراز هویت، گواهی برایش صادر نخواهد شد.

## محتوای دوره‌ها (فصل، درس و فایل)

هر دوره می‌تواند به **فصل** تقسیم شود و هر فصل چند **درس** داشته باشد.

### وارد کردن محتوا در پنل مدیریت

پنل مدیریت جنگو از فرم تودرتوی سه‌طبقه پشتیبانی نمی‌کند، پس ترتیب کار این است:

1. **دوره‌ها ← ویرایش دوره** → در پایین صفحه، فصل‌ها را اضافه و ذخیره کنید
2. کنار هر فصل، روی **«افزودن و ویرایش درس‌ها»** بزنید → درس‌ها را وارد کنید
3. کنار هر درس، روی **«ویرایش محتوا»** بزنید → ویدیو، متن و فایل‌های پیوست

دوره‌ای که فصل ندارد، همان فهرست متنی فیلد «سرفصل‌ها» را نمایش می‌دهد؛
پس لازم نیست همه دوره‌ها را یک‌باره فصل‌بندی کنید.

### پیش‌نمایش رایگان

هر درسی که گزینه **«پیش‌نمایش رایگان»** آن روشن باشد، برای همه
بازدیدکنندگان — حتی بدون حساب کاربری — باز است. معمولاً یکی دو درس اول را
پیش‌نمایش می‌گذارند تا کاربر پیش از خرید، کیفیت دوره را ببیند.

### چرا فایل‌ها در پوشه جداگانه ذخیره می‌شوند؟

فایل‌های ویدیو و جزوه در پوشه `protected_media/` ذخیره می‌شوند، **نه** در
`media/`. دلیلش ساده است: هر چیزی داخل `media/` با یک آدرس ثابت برای همه
باز است. اگر ویدیوی دوره پولی آنجا باشد، کافی است یک نفر آدرس را کپی کند
و برای صد نفر بفرستد.

با این ساختار، تنها راه رسیدن به فایل، آدرس خود درس است و آن آدرس هم قبل
از تحویل فایل بررسی می‌کند کاربر اجازه دارد یا نه.

### تنظیم Nginx در سرور

در محیط توسعه چیزی لازم نیست. در Production بهتر است ارسال فایل را به
Nginx بسپارید تا پایتون برای هر ویدیو چند دقیقه مشغول نماند:

در فایل `.env`:

```env
PROTECTED_MEDIA_ROOT=/srv/hse/protected_media
USE_X_ACCEL_REDIRECT=True
X_ACCEL_REDIRECT_PREFIX=/protected-internal/
```

و در تنظیمات Nginx:

```nginx
location /protected-internal/ {
    internal;                          # فقط با دستور Django قابل استفاده است
    alias /srv/hse/protected_media/;
}
```

کلمه `internal` مهم است: بدون آن، همین مسیر از بیرون قابل صدا زدن می‌شود و
کل محافظت بی‌اثر می‌شود.

### پیگیری پیشرفت دانشجو

پیشرفت به‌صورت خودکار ثبت می‌شود:

- **باز کردن درس** → درس در «دوره‌های من» ظاهر می‌شود
- **دکمه «تکمیل کردم»** → درس تیک می‌خورد و درصد دوره بالا می‌رود
- **ویدیو** → هر ۱۵ ثانیه موقعیت ذخیره می‌شود و دفعه بعد از همان‌جا ادامه می‌یابد

«دیده شده» با «تکمیل شده» فرق دارد: باز کردن درس فقط آن را به فهرست کاربر
اضافه می‌کند؛ تکمیل شدن را خود دانشجو اعلام می‌کند.

دکمه «ادامه یادگیری» همیشه به **اولین درس ناتمام** می‌رود، نه به آخرین
درسی که کاربر باز کرده — وگرنه کاربری که همین حالا درسی را تمام کرده،
دوباره به همان درس برمی‌گشت.

در پنل مدیریت، بخش **«پیشرفت درس‌ها»** فقط‌خواندنی است؛ عددی که مبنای
صدور گواهی می‌شود نباید دستکاری‌شدنی باشد.

## سبد خرید، سفارش و کد تخفیف

### مسیر خرید

```
صفحه دوره → افزودن به سبد → /cart/ → ورود → /checkout/ → ثبت سفارش
```

سبد خرید در **Session** ذخیره می‌شود، نه در دیتابیس. یعنی کاربر مهمان هم
می‌تواند دوره را در سبد بگذارد و بعد ثبت‌نام کند؛ سبدش از بین نمی‌رود.

### دو قاعده مهم درباره پول

**۱. هیچ مبلغی از مرورگر پذیرفته نمی‌شود.**
در Session فقط *شناسه دوره‌ها* و *متن کد تخفیف* ذخیره می‌شود — نه قیمت و نه
مبلغ تخفیف. همه اعداد هربار در سرور و از روی دیتابیس حساب می‌شوند. اگر
قیمت در Session بود، کاربر می‌توانست آن را دستکاری کند و دوره چهار میلیونی
را هزار تومان بخرد.

**۲. فاکتور در لحظه ثبت سفارش عکس‌برداری می‌شود.**
عنوان دوره و قیمتش داخل خود سفارش ذخیره می‌شوند. اگر ماه بعد قیمت دوره
عوض شود، فاکتور قدیمی دست‌نخورده می‌ماند؛ وگرنه کاربر رسیدی می‌دید که با
پولی که پرداخت کرده جور نبود.

به همین دلیل، دوره‌ای که فروخته شده **قابل حذف نیست** (`on_delete=PROTECT`).
اگر لازم است دوره‌ای دیگر ارائه نشود، آن را از انتشار خارج کنید.

### کد تخفیف

در پنل مدیریت، بخش **کدهای تخفیف**:

| تنظیم | کاربرد |
|---|---|
| نوع تخفیف | درصدی یا مبلغ ثابت |
| سقف تخفیف | فقط برای درصدی؛ مثلاً «۳۰٪ تا سقف ۵۰۰ هزار تومان» |
| حداقل مبلغ سفارش | کد فقط بالای این مبلغ اعمال می‌شود |
| حداکثر تعداد استفاده | ظرفیت کل کد |
| حداکثر استفاده هر کاربر | صفر یعنی نامحدود |
| محدود به دوره‌های | خالی یعنی همه دوره‌ها |

شمارنده استفاده فقط با **پرداخت موفق** بالا می‌رود، نه با ثبت سفارش؛ پس
سفارشی که کاربر رها کرده ظرفیت کد را نمی‌سوزاند.

دو کد نمونه با `seed_demo` ساخته می‌شوند: `NOWRUZ` (۲۰٪) و `HSE500`
(۵۰۰ هزار تومان).

### وضعیت سفارش

`در انتظار پرداخت` → `پرداخت شده` / `پرداخت ناموفق` / `لغو شده` / `بازگشت وجه`

**تنها وضعیتی که دسترسی به دوره می‌دهد `پرداخت شده` است**، و تنها راه
رسیدن به آن، تأیید سمت سرورِ درگاه پرداخت است (فاز ۱۲ و ۱۳). ثبت سفارش با
پرداخت یکی نیست.

## درگاه پرداخت

### حالت آزمایشی (پیش‌فرض)

در فایل `.env` مقدار `USE_MOCK_PAYMENT=True` است. یعنی به‌جای بانک، صفحه‌ای
در خود سایت باز می‌شود با دو دکمه: **پرداخت موفق** و **پرداخت ناموفق**.
هیچ پولی جابه‌جا نمی‌شود، اما تمام مسیر — از سبد خرید تا باز شدن دسترسی
دوره — دقیقاً همان‌طور طی می‌شود که در درگاه واقعی طی خواهد شد.

مسیر کامل:

```
/orders/<شماره>/ → دکمه «پرداخت آنلاین» → صفحه درگاه → بازگشت → تأیید سرور → دسترسی باز
```

### چرا این مهم‌ترین بخش امنیتی پروژه است

آدرس بازگشتی درگاه را **مرورگر کاربر** صدا می‌زند، نه خود درگاه. یعنی هر
کسی می‌تواند در نوار آدرس بنویسد:

```
/payments/callback/?Authority=XYZ&Status=OK
```

اگر سایت این را باور کند، دوره چند میلیونی بدون پرداخت یک ریال باز می‌شود.
این رایج‌ترین راه کلاهبرداری از فروشگاه‌های آنلاین ایرانی است.

**در این پروژه پارامتر `Status` اصلاً خوانده نمی‌شود.** فقط `Authority`
برداشته می‌شود تا تراکنش پیدا شود، و بعد سرور ما مستقیماً از درگاه
می‌پرسد: «این تراکنش واقعاً پرداخت شده؟ چقدر؟» تنها اگر پاسخ درگاه مثبت
باشد **و** مبلغ دقیقاً با سفارش بخواند، دسترسی داده می‌شود.

پنج سد پیش از تأیید نهایی بررسی می‌شوند:

1. آیا این تراکنش قبلاً تأیید شده؟ (رفرش صفحه نباید دوباره حساب شود)
2. آیا مهلتش تمام نشده؟
3. آیا سفارش در این فاصله لغو نشده؟
4. **حالا از خود درگاه بپرس** (تماس سرور به سرور)
5. آیا مبلغ تأییدشده دقیقاً با مبلغ سفارش یکی است؟

### تست کردن مسیر ناموفق

روی صفحه درگاه آزمایشی، دکمه **«پرداخت ناموفق»** را بزنید. سفارش در وضعیت
«پرداخت ناموفق» می‌ماند، سابقه تراکنش ثبت می‌شود و کاربر می‌تواند دوباره
تلاش کند. تاریخچه همه تلاش‌ها در صفحه سفارش و در پنل مدیریت دیده می‌شود.

### وصل کردن درگاه واقعی

در فاز ۱۳ انجام می‌شود. وقتی درگاه را خریدید، فقط این‌ها در `.env` عوض
می‌شوند:

```env
USE_MOCK_PAYMENT=False
PAYMENT_PROVIDER=zarinpal
ZARINPAL_MERCHANT_ID=کد-پذیرندگی-شما
ZARINPAL_SANDBOX=False
```

هیچ View، مدل یا قالبی دست نمی‌خورد.

### آنچه ذخیره می‌شود و آنچه نمی‌شود

| ذخیره می‌شود | ذخیره **نمی‌شود** |
|---|---|
| شماره پیگیری بانک | شماره کامل کارت |
| چهار رقم آخر کارت | CVV2 و رمز دوم |
| مبلغ و زمان تراکنش | هیچ اطلاعات هویتی بانکی |

جدول تراکنش‌ها در پنل مدیریت **کاملاً فقط‌خواندنی** است: این جدول سند
مالی است و اگر قابل ویرایش باشد، هنگام اختلاف با بانک یا کاربر نمی‌شود به
آن استناد کرد.

## ثبت‌نام و مدیریت دسترسی

### «ثبت‌نام» یعنی چه؟

یک جمله: **این شخص به این دوره دسترسی دارد.** منبعش هرچه باشد، پاسخ سؤال
دسترسی همیشه از همین‌جا می‌آید:

| منبع | چطور ساخته می‌شود |
|---|---|
| خرید | خودکار، بعد از تأیید پرداخت |
| دوره رایگان | با دکمه «ثبت‌نام رایگان» در صفحه دوره |
| افزودن دستی | پنل مدیریت ← ثبت‌نام‌ها ← افزودن |
| اشتراک ویژه | کاربر ویژه به دوره‌های مجاز دسترسی دارد |

### مدت دسترسی

هر دوره فیلدی به نام **«مدت دسترسی (روز)»** دارد:

- **خالی** → دسترسی دائمی (پیش‌فرض)
- **مثلاً ۹۰** → دانشجو ۹۰ روز از تاریخ خرید دسترسی دارد

انقضا **هربار محاسبه می‌شود**، نه اینکه در دیتابیس ذخیره شود. اگر ذخیره
می‌شد، دسترسی تا اجرای بعدی یک دستور زمان‌بندی‌شده باز می‌ماند — یعنی
ساعت‌ها بعد از تمام شدن مهلت.

**تمدید زودهنگام روزهای باقی‌مانده را نمی‌سوزاند:** اگر کاربری ۲۰ روز
مانده به پایان، دوره را دوباره بخرد، مدت جدید به انتهای دوره فعلی اضافه
می‌شود، نه از امروز.

### بستن دسترسی

در پنل مدیریت، وضعیت ثبت‌نام را روی **تعلیق‌شده** یا **بازگشت وجه**
بگذارید. ردیف ثبت‌نام **حذف نمی‌شود** — حذفش یعنی پاک کردن تاریخچه‌ای که
ممکن است بعداً لازم شود.

### گزارش وضعیت

```bash
python manage.py enrollments
python manage.py enrollments --expiring 30
```

نشان می‌دهد چند نفر دسترسی فعال دارند، پرطرفدارترین دوره‌ها کدام‌اند، و
دسترسی چه کسانی به‌زودی تمام می‌شود.

### تغییری که در این فاز اتفاق افتاد

پیش از این، **هر کاربر واردشده‌ای** به دوره‌های رایگان دسترسی داشت و
«دوره‌های من» از روی درس‌هایی که باز کرده بودید ساخته می‌شد. حالا:

- دوره رایگان هم ثبت‌نام می‌خواهد (یک کلیک) تا بشود فهمید چه کسی دوره را
  می‌گذراند و بعداً برایش گواهی صادر کرد
- دوره‌ای که خریده‌اید ولی هنوز بازش نکرده‌اید، در «دوره‌های من» هست
- دیدن یک درس نمونه رایگان، دوره را به فهرست شما اضافه نمی‌کند

همچنین سفارشی که مبلغش صفر است (دوره رایگان یا تخفیف صددرصدی) دیگر به
درگاه فرستاده نمی‌شود؛ پیش از این چنین سفارشی برای همیشه در حالت
«در انتظار پرداخت» می‌ماند.

## کلاس آنلاین و لینک ورود

### وارد کردن برنامه کلاس‌ها

پنل مدیریت ← **دوره‌ها** ← دوره موردنظر ← پایین صفحه، جدول
**«جلسه‌های آنلاین»**. برای هر جلسه این‌ها را پر کنید:

| فیلد | توضیح |
|---|---|
| عنوان جلسه | مثلاً «جلسه سوم — ارزیابی ریسک در ارتفاع» |
| زمان شروع | تاریخ و ساعت شروع کلاس |
| مدت (دقیقه) | زمان پایان خودکار از روی همین حساب می‌شود |
| آدرس ورود به کلاس | لینکی که از پنل اسکای‌روم کپی می‌کنید |
| درس مرتبط | اختیاری — اگر این جلسه در سرفصل هم یک درس دارد |

### لینک کلاس در کجا دیده می‌شود؟ هیچ‌جا

مهم‌ترین قاعده این بخش: **آدرس کلاس هیچ‌وقت داخل HTML صفحه نوشته
نمی‌شود.** دکمه «ورود به کلاس» به آدرس
`/courses/<slug>/sessions/<id>/join/` می‌رود و آن View پیش از هدایت
کاربر، سه چیز را بررسی می‌کند:

1. جلسه لغو نشده باشد و لینک داشته باشد
2. کاربر در دوره **ثبت‌نام فعال** داشته باشد (خرید، رایگان، دستی یا ویژه)
3. زمانش رسیده باشد

اگر لینک را مستقیم در صفحه می‌گذاشتیم، هر بازدیدکننده‌ای با یک نگاه به
سورس صفحه می‌توانست وارد کلاسی شود که پولش را نداده است. تستِ
«لینک کلاس در صفحه دوره ظاهر نمی‌شود» دقیقاً همین را نگه می‌دارد.

### دکمه ورود کِی فعال می‌شود؟

از **۳۰ دقیقه پیش از شروع** تا **۳۰ دقیقه بعد از پایان** جلسه. هر دو عدد
در `.env` قابل تغییرند:

```
ONLINE_SESSION_JOIN_LEAD_MINUTES=30
ONLINE_SESSION_GRACE_MINUTES=30
```

پیش از آن، دانشجو عنوان و ساعت جلسه را می‌بیند اما دکمه ورود ندارد. مدیر
سایت و مدرسِ خود دوره از این محدودیت مستثنا هستند تا بتوانند زودتر کلاس
را باز کنند.

### دانشجو کلاس‌هایش را کجا می‌بیند؟

- **صفحه دوره** — برنامه جلسه‌های پیش‌رو (برای همه، بدون لینک)
- **داشبورد** — سه کلاس نزدیک
- **داشبورد ← کلاس‌های آنلاین** — همه کلاس‌های پیش‌رو و برگزارشده
- **صفحه درس** — اگر جلسه به یک درس از سرفصل وصل شده باشد

### لغو یک جلسه

وضعیت جلسه را روی **«لغو شده»** بگذارید و در «علت لغو» بنویسید چه شده
است. همان متن به دانشجو نشان داده می‌شود. جلسه حذف نمی‌شود تا در برنامه
دوره بماند.

### اتصال خودکار به اسکای‌روم (اختیاری)

حالت پیش‌فرض `manual` است: یک لینک ثابت برای همه دانشجوهای دوره. اگر
اکانت اسکای‌روم با دسترسی API دارید، در `.env` بنویسید:

```
SKYROOM_PROVIDER=skyroom
SKYROOM_API_KEY=کلید-شما
```

و در پنل مدیریتِ هر جلسه، «شناسه کلاس در اسکای‌روم» را پر کنید. آن‌وقت
برای هر دانشجو یک **لینک ورود شخصی و کوتاه‌مدت** ساخته می‌شود؛ یعنی
فرستادن لینک در گروه تلگرامی دیگر به‌درد کسی نمی‌خورد. نام دانشجو هم به
کلاس فرستاده می‌شود تا مدرس در فهرست حاضرین، اسم واقعی را ببیند.

اگر API در دسترس نباشد، سایت خودکار به همان لینک ثابت برمی‌گردد: کلاس
نباید به‌خاطر قطعی یک سرویس جانبی از دست برود.

## آزمون

### ساخت آزمون

پنل مدیریت ← **آزمون‌ها** ← افزودن. برای هر دوره **حداکثر یک آزمون**
ساخته می‌شود؛ چند آزمون برای یک دوره یعنی باید جایی تصمیم بگیریم کدامشان
ملاک گواهی است، و این سؤال در نسخه اول جوابی جز پیچیدگی ندارد.

| تنظیم | معنی |
|---|---|
| تعداد سؤال هر آزمون | صفر یعنی همه سؤال‌های بانک. عدد کمتر یعنی هر دانشجو سؤال‌های تصادفی متفاوتی می‌گیرد |
| مدت آزمون | صفر یعنی بدون محدودیت زمانی |
| نمره قبولی | درصد لازم برای قبولی (ملاک گواهی در فاز بعد) |
| حداکثر دفعات | صفر یعنی نامحدود |
| نیاز به تکمیل دوره | تا همه درس‌ها تکمیل نشوند، آزمون باز نمی‌شود |
| منتشر شده | تا روشن نشود، فقط مدیر و مدرس دوره آزمون را می‌بینند |

سؤال‌ها را از همان صفحه آزمون یا از بخش **سؤال‌ها** وارد کنید. هر سؤال
چند گزینه دارد و **دقیقاً یکی** باید «پاسخ درست» علامت بخورد؛ سؤالی که
پاسخ درستش مشخص نشده باشد، اصلاً وارد آزمون نمی‌شود (در فهرست سؤال‌ها با
رنگ قرمز مشخص است).

> **سؤال تشریحی فعلاً پشتیبانی نمی‌شود.** فیلدش در مدل هست اما تصحیح
> تشریحی به یک رابط جداگانه برای مدرس نیاز دارد که کار نسخه بعد است.

### زمان‌سنج کجا اجرا می‌شود؟ در سرور

مهلت آزمون در لحظه شروع محاسبه و **در دیتابیس ذخیره** می‌شود. شمارنده‌ای
که دانشجو در صفحه می‌بیند فقط برای راحتی اوست؛ دستکاری آن در مرورگر یا
خاموش کردن جاوااسکریپت، یک ثانیه هم وقت اضافه نمی‌دهد چون هر پاسخ پیش از
ذخیره، با مهلتِ سرور سنجیده می‌شود.

اگر مدیر وسط آزمون مدت آزمون را عوض کند، مهلت کسی که مشغول است جابه‌جا
نمی‌شود.

**ارفاق چند ثانیه‌ای:** ثبت نهایی دانشجو چند ثانیه در راه است. مقدار
`EXAM_SUBMIT_GRACE_SECONDS` (پیش‌فرض ۶۰ ثانیه) باعث می‌شود پاسخ کسی که در
ثانیه آخر دکمه را زده دور ریخته نشود.

### اگر مرورگر بسته شود یا اینترنت قطع شود؟

هر پاسخ **همان لحظه انتخاب** در سرور ذخیره می‌شود، نه فقط موقع «ثبت
نهایی». اگر مهلت تمام شود یا دانشجو صفحه را ببندد، آزمون با همان پاسخ‌های
ثبت‌شده تصحیح می‌شود و کارنامه‌اش با برچسب «ثبت خودکار» ذخیره می‌شود.

بدون جاوااسکریپت هم آزمون کامل کار می‌کند — فقط ذخیره لحظه‌ای را از دست
می‌دهید و پاسخ‌ها موقع ثبت نهایی می‌روند.

### چرا کارنامه‌ها قابل ویرایش نیستند؟

نمره، امتیاز، نمره قبولی و نتیجه، **در لحظه تصحیح** داخل کارنامه نوشته
می‌شوند. اگر ماه بعد مدرس یک گزینه اشتباه را اصلاح کند یا امتیاز سؤالی را
عوض کند، کارنامه‌های قبلی تکان نمی‌خورند — وگرنه گواهی صادرشده با کارنامه
پشتش نمی‌خواند.

به همین دلیل سؤالی که کسی به آن پاسخ داده **پاک نمی‌شود**. برای کنار
گذاشتن یک سؤال، آن را **غیرفعال** کنید؛ از آن به بعد در آزمون‌های تازه
نمی‌آید و کارنامه‌های قبلی هم سالم می‌مانند.

### مسیر دانشجو

```
صفحه دوره → صفحه آزمون (قوانین) → شروع → برگه امتحان → ثبت نهایی → کارنامه
```

کارنامه‌ها در **داشبورد ← آزمون‌ها** هم فهرست می‌شوند. اگر دانشجو وسط
آزمون صفحه را ببندد، دکمه «ادامه آزمون» همان برگه را با همان سؤال‌ها و
پاسخ‌های ذخیره‌شده باز می‌کند — سؤال‌های تصادفی در لحظه شروع قفل شده‌اند.

## گواهی پایان دوره

### گواهی چه زمانی صادر می‌شود؟

گواهی **خودکار صادر نمی‌شود**؛ دانشجو دکمه «دریافت گواهی» را می‌زند. اما
آن دکمه فقط وقتی ظاهر می‌شود که **همه** این شرط‌ها برقرار باشند:

| شرط | چرا |
|---|---|
| دوره گواهی داشته باشد | فیلد «دارای گواهی» در تنظیمات دوره |
| ثبت‌نام فعال | گواهی مدرک گذراندن دوره است، نه مدرک دسترسی — مدیر و مدرس گواهی نمی‌گیرند |
| نام و نام خانوادگی ثبت‌شده | همین نام روی گواهی چاپ می‌شود |
| تأیید شماره موبایل | |
| احراز هویت (کد ملی) | گواهی فقط به نام فردی صادر می‌شود که هویتش تأیید شده |
| تکمیل همه درس‌ها | |
| قبولی در آزمون | اگر دوره آزمون فعال داشته باشد |

اگر شرطی برقرار نباشد، دانشجو در صفحه دوره **دقیقاً همان یک قدم بعدی** را
می‌بیند (مثلاً «۲ درس باقی مانده» یا «احراز هویت»)، نه یک پیام کلی.

### کد گواهی و توکن استعلام — چرا دو تا؟

روی هر گواهی یک کد مثل `HSE-1405-00001` چاپ می‌شود: کوتاه، ترتیبی و قابل
خواندن روی تلفن. اما همین ترتیبی‌بودن یعنی می‌شود کدها را یکی‌یکی شمرد؛
اگر لینک QR هم روی همین کد ساخته می‌شد، هر کسی می‌توانست گواهی همه
دانشجوها را بیرون بکشد.

برای همین آدرس داخل QR روی یک **توکن تصادفی** ساخته می‌شود. کد برای
آدم‌هاست، توکن برای لینک.

صفحه استعلام (`/certificate/verify/`) هر دو راه را می‌پذیرد: کد تایپ‌شده
و توکنِ داخل QR. تفاوتشان در بخش «استعلام عمومی گواهی» توضیح داده شده است.

### اطلاعات گواهی عکس‌برداری می‌شوند

نام دانشجو، عنوان دوره، مدت، نام مدرس و نمره در **لحظه صدور** داخل خود
گواهی نوشته می‌شوند. اگر بعداً عنوان دوره عوض شود یا دانشجو نامش را در
پروفایل اصلاح کند، گواهیِ چاپ‌شده در دست کارفرما با آنچه سایت نشان
می‌دهد می‌خواند — و همین، معنای «اصالت» است.

### ابطال گواهی

پنل مدیریت ← گواهی‌ها ← وضعیت را روی **باطل‌شده** بگذارید و علتش را
بنویسید. گواهی **حذف نمی‌شود**: صفحه استعلام باید بتواند بگوید «این گواهی
باطل شده است»، نه «چنین گواهی‌ای وجود ندارد». فایل PDF گواهی باطل‌شده هم
با مهر قرمز «باطل‌شده» ساخته می‌شود.

گواهی از پنل **ساخته هم نمی‌شود**؛ صدور دستی یعنی دور زدن همان شرط‌هایی
که گواهی را معتبر می‌کنند.

### فایل PDF چطور ساخته می‌شود؟

روی خود سرور، بدون هیچ سرویس آنلاین — تا روزی که آن سرویس قطع است، صدور
گواهی متوقف نشود و اطلاعات هویتی دانشجو از سرور بیرون نرود.

برای این کار چهار کتابخانه به پروژه اضافه شده (همه پایتون خالص و بدون
نیاز به کامپایل روی ویندوز):

| کتابخانه | کار |
|---|---|
| `reportlab` | ساخت خود فایل PDF |
| `qrcode` | QR استعلام |
| `arabic-reshaper` | چسباندن حروف فارسی (ب ← بـ ← ـبـ ← ـب) |
| `python-bidi` | چیدن متن راست‌به‌چپ |

دو کتابخانه آخر لازم‌اند چون موتور PDF این دو کار را خودش انجام نمی‌دهد؛
بدون آن‌ها حروف فارسی **جدا و برعکس** چاپ می‌شوند.

فونت گواهی همان Vazirmatn پروژه است — نسخه TTF آن کنار فایل‌های woff2
سایت در `static/fonts/vazirmatn/` قرار دارد، پس ساخت گواهی به هیچ فونت
سیستمی یا اینترنت وابسته نیست.

فایل PDF ذخیره نمی‌شود و در هر بار دانلود ساخته می‌شود؛ این‌طور نسخه‌ای که
دانلود می‌شود همیشه با وضعیت همان لحظه می‌خواند.

## استعلام عمومی گواهی

آدرس `/certificate/verify/` — بدون نیاز به حساب کاربری. این تنها جای سایت
است که یک غریبه به داده‌های یک دانشجو نگاه می‌کند، پس دو نگرانی هم‌زمان
دارد:

- **کارفرما باید بتواند اصالت را بررسی کند** — وگرنه گواهی فقط کاغذ است.
- **کسی نباید با شمردن کدها فهرست دانشجوها را جمع کند** — کد گواهی
  ترتیبی است و همین یعنی حدس‌زدنی.

تعادل این دو با یک قاعده ساده بسته شده است:

| راه استعلام | چه چیزی نشان داده می‌شود |
|---|---|
| **کد** (تایپ‌شده از روی کاغذ) | نام کوتاه‌شده: «سارا م.» |
| **توکن** (اسکن QR روی گواهی) | نام کامل: «سارا محمدی» |

کسی که QR را اسکن می‌کند خودِ گواهی را در دست دارد؛ نام کامل چیزی را به
او لو نمی‌دهد. اما کسی که فقط کدها را می‌شمارد، به اسم کامل هیچ‌کس
نمی‌رسد. **شماره موبایل، کد ملی و ایمیل در هیچ حالتی وارد این صفحه
نمی‌شوند.**

### سه جواب متفاوت، نه یک پیام کلی

| وضعیت | چه چیزی نشان داده می‌شود |
|---|---|
| معتبر | کادر سبز + مشخصات دوره، تاریخ صدور و نمره |
| باطل‌شده | کادر قرمز + **علت ابطال** |
| منقضی‌شده | کادر نارنجی + تاریخ پایان اعتبار |
| پیدا نشد | پیام جداگانه با شماره تماس پشتیبانی |

«پیدا نشد» و «باطل شده» هیچ‌وقت در یک پیام قاطی نمی‌شوند؛ این دو برای
کارفرما دو حرف کاملاً متفاوت‌اند.

### کد را همان‌طور که مردم می‌نویسند می‌خوانیم

کسی که کد را از روی کاغذ تایپ می‌کند ممکن است ارقام فارسی بنویسد، حروف
کوچک بزند، یا فاصله و خط تیره اضافه کند. همه اینها پیش از جست‌وجو یکدست
می‌شوند:

```
hse – ۱۴۰۵ – ۰۰۰۰۱   →   HSE-1405-00001
```

### محدودیت تعداد استعلام

هر IP در ساعت حداکثر `CERTIFICATE_LOOKUP_MAX_PER_HOUR` استعلام (پیش‌فرض
۳۰) می‌تواند انجام دهد. باز کردن خود صفحه شمرده نمی‌شود — فقط جست‌وجوی
واقعی. این عدد در حدی است که هیچ کارفرمای واقعی به آن نمی‌خورد، اما
امتحان‌کردن کدها یکی‌یکی را بی‌فایده می‌کند.

صفحه نتیجه با `noindex` علامت‌گذاری می‌شود تا کارنامه کسی در نتایج
جست‌وجوی گوگل بالا نیاید.

## مقاله و خبر (در نسخه اول خاموش)

بخش مقالات **زیرساختش کامل ساخته شده** اما صفحات عمومی‌اش خاموش‌اند:

```
BLOG_ENABLED=False      # پیش‌فرض
```

با این مقدار، آدرس‌های `/blog/` همگی **۴۰۴** می‌دهند و هیچ لینکی هم در
منو و فوتر ظاهر نمی‌شود. اما **پنل مدیریت مقالات همیشه کار می‌کند** —
مستقل از این کلید.

چرا این‌طور؟ نوشتن ده مقاله خوب کارِ چند هفته یک نویسنده است، نه کار
برنامه‌نویس. تیم محتوا از همین حالا مطلب‌ها را وارد می‌کند و در پنل
می‌بیند؛ روزی که مطلب کافی آماده شد، `BLOG_ENABLED=True` می‌شود و بخش
مقالات با محتوای واقعی بالا می‌آید — بدون یک خط تغییر در کد و بدون
مهاجرت تازه.

> **چرا ۴۰۴ و نه صفحه «به‌زودی»؟** صفحه «به‌زودی» به گوگل می‌گوید این آدرس
> وجود دارد و ایندکسش می‌کند؛ بعداً باید همان آدرسِ ایندکس‌شده را با
> محتوای واقعی عوض کنیم. تا وقتی مطلبی برای نشان دادن نیست، بهتر است این
> بخش اصلاً وجود نداشته باشد.

### سه حالت انتشار

| وضعیت | در سایت دیده می‌شود؟ |
|---|---|
| پیش‌نویس | نه |
| منتشرشده با تاریخ گذشته | بله |
| منتشرشده با تاریخ آینده | نه — تا رسیدن همان لحظه («زمان‌بندی‌شده») |
| بایگانی‌شده | نه |

زمان‌بندی یعنی نویسنده می‌تواند پنج مطلب را یک روز بنویسد و برای پنج
هفته بعد تنظیم کند. ضمناً **غیرفعال کردن یک دسته‌بندی، همه مطالبش را هم
از سایت برمی‌دارد**؛ نیازی به دست زدن به تک‌تک مطلب‌ها نیست.

مدیر سایت می‌تواند مطلب منتشرنشده را از آدرس خودش **پیش‌نمایش** کند (با
نوار هشدار بالای صفحه و `noindex`)؛ برای بقیه همان آدرس ۴۰۴ است.

### مقاله و خبر در یک جدول‌اند

ساختارشان یکی است (عنوان، متن، تصویر، نویسنده) و تفاوتشان فقط در نحوه
نمایش است. دو جدول جدا یعنی دو پنل مدیریت، دو صفحه فهرست و دو نسخه از هر
تغییر آینده. نوع مطلب با فیلد «نوع» مشخص می‌شود و صفحه فهرست، فیلترش را
دارد.

**زمان مطالعه** خودکار از روی تعداد کلمه‌ها تخمین زده می‌شود (۲۰۰ کلمه در
دقیقه) و در پنل مدیریت هم کنار متن نشان داده می‌شود.

## سئو

سئو در این پروژه یک کار جداگانه در انتها نبود؛ از فاز اول رعایت شده است
(رندر سمت سرور، آدرس‌های معنادار فارسی، عنوان و توضیح اختصاصی هر صفحه).
در این فاز چهار چیز به آن اضافه شد.

### ۱. نقشه سایت — `/sitemap.xml`

خودکار از روی داده‌های واقعی ساخته می‌شود: صفحه‌های ثابت، دوره‌های
**منتشرشده**، دسته‌بندی‌های فعال، مدرسان فعال و (اگر بخش مقالات روشن
باشد) مطالب منتشرشده.

دو قاعده در آن رعایت شده:

- **فقط چیزی که واقعاً عمومی است.** دوره منتشرنشده، مقاله پیش‌نویس و هر
  صفحه‌ای که ورود می‌خواهد در نقشه سایت نمی‌آید. آدرس خصوصی در نقشه سایت
  یعنی دعوت مستقیم از خزنده به جایی که نباید برود.
- **`lastmod` از خود داده می‌آید،** نه از تاریخ امروز. اگر هر بار «همین
  حالا» بفرستیم، گوگل بعد از چند بار می‌فهمد این عدد بی‌معنی است.

### ۲. `robots.txt`

با View ساخته می‌شود نه فایل ثابت، چون آدرس نقشه سایت باید با دامنه واقعی
همان درخواست نوشته شود. مسیرهای شخصی و خرید (داشبورد، سبد، پرداخت، آزمون،
گواهی، پنل مدیریت) بسته‌اند.

> **بستن در `robots.txt` جای کنترل دسترسی را نمی‌گیرد.** آن کار در خود
> Viewها انجام می‌شود؛ این فقط به خزنده می‌گوید وقتش را تلف نکند.

### ۳. داده ساختاریافته (JSON-LD)

| صفحه | نوع داده | فایده |
|---|---|---|
| صفحه اصلی | `EducationalOrganization` + `WebSite` | کارت دانش کنار نتایج + کادر جست‌وجوی مخصوص سایت |
| دوره | `Course` با قیمت و تاریخ | نمایش قیمت و تاریخ شروع در نتیجه جست‌وجو |
| مدرس | `Person` | |
| سؤالات متداول | `FAQPage` | باز شدن سؤال و جواب زیر نتیجه گوگل |
| مقاله و خبر | `Article` / `NewsArticle` | |
| همه صفحه‌ها | `BreadcrumbList` | نمایش مسیر به‌جای آدرس خام |

قاعده ثابت: **داده ساختاریافته هیچ‌وقت چیزی نمی‌گوید که روی صفحه نیست.**
ادعای اضافه (مثل امتیاز جعلی) هم خلاف واقع است و هم جریمه سئو دارد.

### ۴. آدرس اصلی (canonical) و صفحه‌های تکراری

صفحه دوره‌ها با هر ترکیب فیلتر یک آدرس تازه می‌سازد. از نظر گوگل اینها
ده‌ها صفحه با محتوای تقریباً یکسان‌اند و اعتبار صفحه اصلی بینشان خرد
می‌شود. قاعده‌ای که پیاده شده:

| آدرس | وضعیت |
|---|---|
| `/courses/` | ایندکس می‌شود |
| `/courses/?category=safety` | **ایندکس می‌شود** — این صفحه دسته‌بندی سایت است |
| `/courses/?page=2` | ایندکس می‌شود، با canonical خودش |
| `/courses/?sort=cheapest` و هر فیلتر دیگر | `noindex`، canonical به `/courses/` |
| `/search/?q=…` | همیشه `noindex` |

صفحه دوم فهرست محتوای متفاوتی دارد؛ اشاره‌دادن canonical آن به صفحه اول
یعنی گفتن دروغ به موتور جست‌وجو.

### سرور آزمایشی را ببندید

```
SEO_ALLOW_INDEXING=False
```

با این تنظیم، `robots.txt` کل سایت را می‌بندد **و** همه صفحه‌ها تگ
`noindex, nofollow` می‌گیرند. اگر نسخه آزمایشی ایندکس شود، گوگل دو سایت
با محتوای یکسان می‌بیند و اعتبار سایت اصلی را هم پایین می‌آورد.

**بعد از استقرار روی دامنه واقعی:** آدرس `https://دامنه-شما/sitemap.xml`
را در Google Search Console ثبت کنید.

## امنیت

امنیت در این پروژه یک فاز جداگانه در انتها نبود؛ هر بخش قاعده خودش را از
همان روز اول داشت (هش کردن رمز و کد یکبارمصرف، تأیید سمت‌سرور پرداخت،
بررسی ثبت‌نام پیش از هر محتوای پولی). در این فاز، همه‌ی آن‌ها بازبینی شدند
و چهار لایه‌ی مشترک اضافه شد.

### ۱. محدودسازی نرخ درخواست

هر فرم عمومی، اگر سقف نداشته باشد، با یک اسکریپت ساده قابل سوءاستفاده
است. سقف‌ها ساعتی و به‌ازای هر IP هستند:

| مسیر | پیش‌فرض (در ساعت) | تنظیم |
|---|---|---|
| تماس با ما | ۱۰ | `CONTACT_MAX_PER_HOUR` |
| ثبت‌نام | ۴۰ | `REGISTRATION_MAX_PER_HOUR` |
| بازیابی رمز | ۲۰ | `PASSWORD_RESET_MAX_PER_HOUR` |
| ورود به پنل مدیریت | ۲۰ | `ADMIN_LOGIN_MAX_PER_HOUR` |
| استعلام گواهی | ۳۰ | `CERTIFICATE_LOOKUP_MAX_PER_HOUR` |

اینها **جدا از** محدودیت‌های قبلی‌اند: تلاش ناموفق ورود (روی ترکیب موبایل
و IP) و سقف ارسال کد یکبارمصرف (روی هر شماره) از فازهای قبل سر جایشان
هستند. سقف تازه روی **IP** است و همان چیزی را می‌گیرد که سقف شماره
نمی‌گرفت: کسی که با هزار شماره‌ی مختلف کار می‌کند.

> **چرا اعداد سخاوتمندند؟** در ایران یک شرکت یا آموزشگاه معمولاً با یک IP
> مشترک به اینترنت وصل است و ثبت‌نام گروهی ده‌ها کارمند از همان IP اتفاق
> عادی است — نه حمله. سقف باید جلوی اسکریپت را بگیرد، نه جلوی مشتری
> سازمانی را. صفر یعنی بدون محدودیت.

**فرم ورود پنل مدیریت** فرم خود جنگو است و از محدودیت صفحه ورود سایت رد
نمی‌شود؛ برای همین جداگانه محدود شده است. پنل مدیریت ارزشمندترین هدف
سایت است: یک حساب مدیر یعنی دسترسی به همه دوره‌ها، سفارش‌ها و اطلاعات
کاربران.

### ۲. اعتماد نکردن به هدر `X-Forwarded-For`

همه سقف‌های بالا روی IP کاربر حساب می‌شوند. اگر IP را همیشه از هدر
`X-Forwarded-For` بخوانیم، دور زدن هر سقفی به اندازه فرستادن یک هدر
ساختگی آسان است: هر درخواست، یک IP تازه.

پس این هدر فقط وقتی باور می‌شود که تنظیمات بگوید سایت پشت Proxy خودمان
است (`TRUST_X_FORWARDED_FOR=True`، پیش‌فرض Production). در آن حالت
**Nginx باید هدر را خودش بازنویسی کند**:

```nginx
proxy_set_header X-Forwarded-For $remote_addr;
```

### ۳. سیاست امنیتی محتوا (CSP)

چون این پروژه از فاز اول هیچ فایل جاوااسکریپت، CSS یا فونت خارجی ندارد،
می‌توانستیم سخت‌گیرترین حالت ممکن را بگذاریم:

```
script-src 'self'
```

یعنی مرورگر اجازه ندارد هیچ اسکریپتی جز فایل‌های خود سایت اجرا کند. این
**آخرین خط دفاع در برابر XSS** است: اگر روزی با یک اشتباه در یک قالب،
متنی از کاربر بدون Escape داخل صفحه برود، باز هم اجرا نمی‌شود.

- بلوک‌های داده ساختاریافته (JSON-LD) درون‌خطی‌اند و در هر پاسخ یک
  `nonce` تصادفی می‌گیرند تا در مرورگرهای سخت‌گیر حذف نشوند.
- `style-src` ناچاراً `'unsafe-inline'` دارد (چند قالب از `style` درون‌خطی
  برای متغیرهای CSS استفاده می‌کنند). خطر CSS تزریقی در برابر اسکریپت
  ناچیز است.
- `CSP_REPORT_ONLY=True` برای روزهای اول استقرار: سیاست اعمال نمی‌شود و
  تخلف‌ها فقط در کنسول مرورگر دیده می‌شوند.
- `Permissions-Policy` دسترسی صفحه به دوربین، میکروفون و موقعیت مکانی را
  می‌بندد؛ سایت به هیچ‌کدام نیاز ندارد.

### ۴. نشست و کوکی

| تنظیم | مقدار | چرا |
|---|---|---|
| `SESSION_COOKIE_AGE` | ۱۴ روز | کاربری که دوره خریده نباید هر روز وارد شود؛ نشست ابدی هم روی کامپیوتر مشترک خطرناک است |
| `SESSION_COOKIE_SAMESITE` | `Lax` | لایه دفاع اضافه در برابر CSRF، روی محافظت خود جنگو |
| `SESSION_COOKIE_HTTPONLY` | `True` | جاوااسکریپت به کوکی نشست دسترسی ندارد |

در Production کوکی‌ها فقط روی HTTPS فرستاده می‌شوند و HSTS فعال است
(`config/settings/prod.py`).

### چک‌لیست پیش از تحویل

```bash
python manage.py check --deploy --settings=config.settings.prod
```

این دستور باید **بدون هیچ هشداری** تمام شود. در آخرین اجرا چنین بود.

موارد دیگری که در بازبینی این فاز بررسی و تأیید شدند:

- **دسترسی به داده دیگران** (IDOR): سفارش، کارنامه آزمون، گواهی و فایل
  دوره همگی روی `user` فیلتر می‌شوند — نه فقط روی شناسه توی آدرس
- **پیمایش مسیر**: آدرس فایل محافظت‌شده نمی‌تواند از پوشه خودش بیرون
  برود (تست دارد)
- **افشای وجود حساب**: پیام بازیابی رمز و پیام خطای ورود، هیچ‌کدام
  نمی‌گویند شماره در سایت هست یا نه
- **بازگشت باز (Open Redirect)**: پارامتر `next` فقط آدرس‌های همین سایت
  را می‌پذیرد
- **لاگ**: کد یکبارمصرف خام، رمز و اطلاعات کارت هیچ‌جا لاگ نمی‌شوند؛
  شماره موبایل ماسک‌شده ثبت می‌شود

> **نکته Production:** شمارنده‌های محدودسازی در Cache نگه داشته می‌شوند و
> Gunicorn چند Worker دارد. تنظیمات Production عمداً `DatabaseCache`
> استفاده می‌کند تا شمارنده بین Workerها مشترک باشد؛ با کش حافظه‌ای، سقف
> عملاً چند برابر می‌شد. یک‌بار اجرا کنید:
> `python manage.py createcachetable`

## اجرای تست‌ها

```bash
python manage.py test
```

بیش از **۷۰۰ تست** که در چند ثانیه اجرا می‌شوند. اگر همه سبز بودند،
یعنی زنجیره «ورود → خرید → یادگیری → آزمون → گواهی → استعلام» سالم است.

### اندازه‌گیری پوشش

```bash
coverage run manage.py test
coverage report          # جدول خلاصه در ترمینال
coverage html            # گزارش کامل در htmlcov/index.html
```

پوشش فعلی: **۹۱٪** از خطوط و شاخه‌های کد (بدون احتساب مهاجرت‌ها و
داده نمونه). عدد پوشش به‌تنهایی معنا ندارد؛ چیزی که اهمیت دارد این است
که **کدام** بخش‌ها تست دارند:

| بخش | چه چیزی تضمین شده |
|---|---|
| مسیر کامل دانشجو | یک تست، کل زنجیره را از ثبت‌نام تا استعلام گواهی طی می‌کند |
| پرداخت | سفارش پرداخت‌نشده هیچ دری باز نمی‌کند؛ ادعای موفقیت در آدرس بازگشت بی‌اثر است |
| ماتریس دسترسی | برای هر آدرس حساس، هر چهار نقش (مهمان، غریبه، دانشجو، مدیر) سنجیده می‌شود |
| آزمون | مهلت در سرور، تصحیح خودکار، و تغییرنکردن کارنامه‌های قبلی |
| گواهی | شرط‌های صدور، ساخته‌شدن واقعی PDF، و ماسک‌شدن نام در استعلام با کد |
| امنیت | سقف‌های نرخ، هدرهای امنیتی، پیمایش مسیر، افشا نکردن وجود حساب |
| پنل مدیریت | همه صفحه‌های فهرست/افزودن/ویرایش باز می‌شوند و عملیات گروهی کار می‌کنند |
| دستورهای مدیریتی | گزارش دسترسی‌ها، ساخت گروه‌ها و حساب مدیر |
| تنظیمات Production | بدون خطا خوانده می‌شوند و جلوی تنظیم خطرناک را می‌گیرند |

### یک محافظ که ارزش دانستن دارد

اگر فایل `.env` محیط توسعه روی سرور کپی شود، `USE_MOCK_PAYMENT=True` هم
با خودش می‌رود — یعنی **درگاه آزمایشی روی سایت واقعی**، و هر بازدیدکننده
می‌تواند با یک کلیک «پرداخت موفق»، دوره چند میلیونی را رایگان بردارد.
هیچ خطایی هم در لاگ نمی‌آید، چون کد دقیقاً طبق تنظیمات کار کرده است.

برای همین سایت با این تنظیم **اصلاً بالا نمی‌آید** و پیام روشن می‌دهد.
پیامک و استعلام هویت آزمایشی مجازند (ممکن است پنل هنوز خریداری نشده
باشد) اما باید صریح اعلام شوند:

```
ALLOW_MOCK_SERVICES=True
```

## نکات مهم

**اسلایدر صفحه اصلی:** تصاویر از پنل مدیریت ← «اسلایدهای صفحه اصلی» آپلود می‌شوند.
روی اسلاید هیچ متنی نوشته نمی‌شود، پس کل پیام باید داخل خود تصویر باشد.
اندازه پیشنهادی ۱۹۲۰×۶۵۰ پیکسل. چرخش خودکار هر ۵ ثانیه است و کاربر با دکمه‌های
کناری، نقطه‌های پایین یا کشیدن انگشت هم می‌تواند جابه‌جا شود.

**تاریخ‌ها شمسی هستند.** تبدیل میلادی به شمسی بدون کتابخانه خارجی و در فایل
`apps/core/jalali.py` انجام می‌شود؛ صحت آن با تست بررسی شده است.

**فایل `.env` را در گیت قرار ندهید.** این فایل در `.gitignore` هست. اگر کلیدی به
اشتباه commit شد، باید آن کلید را باطل و کلید جدید بسازید.

**وابستگی به اینترنت خارجی:** تمام فایل‌های CSS، JS، فونت و آیکون به‌صورت محلی در
پوشه `static/` نگهداری می‌شوند. از Google Fonts یا CDN خارجی استفاده نمی‌کنیم تا
سایت در زمان اختلال اینترنت بین‌الملل هم کامل بالا بیاید.

**سرویس‌های خارجی در حالت Mock:** پیامک، استعلام هویت و پرداخت در محیط توسعه
شبیه‌سازی شده‌اند (`USE_MOCK_SMS`، `USE_MOCK_IDENTITY`، `USE_MOCK_PAYMENT` در فایل
`.env`). یعنی می‌توانید کل جریان ثبت‌نام تا خرید را بدون خرید هیچ سرویسی تست کنید.

## تنظیم VS Code

فایل `.vscode/settings.json` از قبل آماده است. فقط یک نکته برای **ویندوز**: مسیر
مفسر پایتون را به این تغییر دهید:

```json
"python.defaultInterpreterPath": "${workspaceFolder}\\.venv\\Scripts\\python.exe"
```

یا ساده‌تر: `Ctrl+Shift+P` → `Python: Select Interpreter` → گزینه‌ای که داخل آن
`.venv` نوشته شده را انتخاب کنید.
